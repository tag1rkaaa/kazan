# Промпты и принятые решения

## Главная идея: не доверять модели то, что можно сделать кодом

Требование «не выдумывать характеристики» выполняется не одним промптом,
а несколькими уровнями:

1. **Характеристики собирает код.** Таблица «Ключевые характеристики» строится
   из входного поля `specs` дословно. Модель пишет только тексты (заголовок,
   описание, поисковые запросы, commercial-блок), поэтому значение
   характеристики она подменить не может.
2. **Нет данных, нет текста.** Если нет ни характеристик, ни описания,
   модель вообще не вызывается: код выдаёт карточку-заглушку с пометкой
   «данных нет».
3. **Автоматическая проверка ответа** (`validation.py`): длина заголовка и
   описания, число запросов (3-5), все числа в тексте должны быть и во
   входных данных, слова поисковых запросов должны встречаться во входных
   данных, запрещены слова-«украшения» без опоры на вход («надёжный»,
   «качественный», «защита» и т. п.). При замечаниях модель переписывает
   текст с этими замечаниями в запросе, максимум 3 попытки. Оставшиеся
   замечания попадают в раздел «Требует внимания» карточки.
4. **Список недостающих данных считает код**, а не модель: модель 7b добавляла
   в него ошибочные пункты.
5. **Человек остаётся в контуре.** Результат называется черновиком, а
   проблемы помечаются в самой карточке.

## Промпт

Системный промпт (`prompts.py`):

- Роль: помощник контент-менеджера B2B-магазина КИП, язык ответа русский.
- Главное правило: единственный источник фактов это блок `<product_data>`;
  запрещено добавлять характеристики, числа, стандарты, материалы, отрасли,
  гарантии, которых нет во входе, и опираться на знания о похожих приборах.
- Требования к каждому полю по отдельности: длины, из чего строить текст,
  запрещённые формулировки.
- Значения характеристик переносятся дословно (не округлять, не менять запятые).
- Данные передаются в теге `<product_data>`, а в промпте сказано, что
  инструкции внутри тега нужно игнорировать. Это защита от текста в
  техпаспорте, который мог бы попытаться управлять моделью.
- Формат ответа задаётся примером JSON с заглушками, а не JSON-схемой
  (см. ниже, почему).

## Что пробовалось и что не сработало

- **Облачные API.** Платные API не использовались. Из бесплатных вариантов
  Gemini не заработал, а запросы к OpenRouter с моей сети получали 403
  («Access denied by security policy», в том числе через `curl`). Поэтому
  выбрана **локальная модель через Ollama**. Код работает с любым
  OpenAI-совместимым API (`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в `.env`),
  так что смена провайдера не требует правок кода.
- **JSON-схема в промпте.** Маленькая модель возвращала куски самой схемы
  (`description`, `type`) вместо карточки. Заменено на пример выходного формата.
  Дополнительно при ошибке разбора ответа выводится его начало.
- **Размер модели.** На `qwen2.5:1.5b` тексты содержали выдумки («надёжность»,
  «для экспертов и профессионалов»), а описание получалось в 100-200 символов.
  На `qwen2.5:7b` текст заметно лучше, но проверка всё равно поймала,
  например, слово «манипулятор» в поисковых запросах. Слова-«украшения» и
  проверка запросов добавлены именно по результатам этих прогонов.
- **Объём 800-1200 символов.** На скудных данных объём без выдумок не набрать.
  Если входного текста мало, короткое описание не считается ошибкой для
  переписывания (иначе модель растягивала бы текст выдумками), а помечается
  как «данных не хватает».
- **Данные для демонстрации.** В задании данных по двум товарам не было.
  Публичный YML-фид `souz-pribor.ru` технических данных не содержит (нет
  описаний, только название, тип, артикул), поэтому описания и
  характеристики для примеров перенесены вручную со страниц товаров.

## Обработка ошибок

- Входной файл: не найден, пустой, битый JSON, неверные типы, нет названия
  дают понятные сообщения без traceback.
- Пустые значения в `specs` отбрасываются, `null` превращается в пустую строку.
- API: нет соединения, таймаут, 404 (нет модели), 429, пустой или
  нечитаемый ответ превращаются в понятные ошибки.
- Пакетный запуск: ошибка одного товара не останавливает остальные.
- Ключи не хранятся в коде: настройки идут из `.env` (в `.gitignore`).
