# Генератор черновиков карточек товаров (КИП)

Прототип сервиса для контент-менеджера B2B-магазина. По JSON с данными о
контрольно-измерительном приборе генерирует черновик карточки товара:
SEO-заголовок, SEO-описание, список характеристик, поисковые запросы и
commercial-блок для менеджера.

Ключевой принцип: **сервис не выдумывает характеристики**. Список
характеристик собирает код из входных данных, а текст модели проходит
автоматическую проверку (подробнее в разделе «Как это работает»).

## Требования

- Python 3.10+
- [Ollama](https://ollama.com/download) с моделью `qwen2.5:7b`
  (или другой OpenAI-совместимый API, см. «Настройка»)

## Установка

```powershell
git clone <ссылка-на-репозиторий>
cd product-card-ai
python -m venv .venv
.\.venv\Scripts\Activate.ps1        # Linux/macOS: source .venv/bin/activate
python -m pip install -r requirements.txt
Copy-Item .env.example .env         # Linux/macOS: cp .env.example .env
ollama pull qwen2.5:7b
```

## Настройка

Параметры задаются в `.env` (файл в `.gitignore`, в репозиторий не попадает):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_BASE_URL` | адрес OpenAI-совместимого API | `http://localhost:11434/v1` (Ollama) |
| `LLM_API_KEY` | ключ API (для Ollama любое непустое значение) | `ollama` |
| `LLM_MODEL` | имя модели | `qwen2.5:7b` |

Проверка настройки: `python check_setup.py`

## Запуск

```powershell
python main.py examples\manometer.json
python main.py examples\manometer.json examples\manometer_full.json --out examples\results
```

Можно передать несколько файлов: ошибка в одном не останавливает остальные.
Для каждого товара создаются два файла в папке результатов (по умолчанию `output/`):
`<имя>.md` для чтения и копирования и `<имя>.json` для автоматической обработки.

Параметры: `--out ПАПКА` задаёт папку результатов, `--quiet` отключает вывод в консоль.

## Формат входных данных

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": { "диапазон измерений": "0–1,6 МПа", "класс точности": "1,5" },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только `name`. Остальные поля можно не указывать: сервис отметит
недостающее в разделе «Требует внимания».

## Как это работает

1. **Загрузка и валидация** (`loader.py`, `models.py`): понятные ошибки для
   отсутствующего или пустого файла, битого JSON, неверных типов. Пустые
   значения характеристик отбрасываются.
2. **Нет данных, нет текста** (`generator.py`): если нет ни характеристик, ни
   описания, модель не вызывается; карточка-заглушка помечена «данных нет».
3. **Генерация** (`prompts.py`, `llm.py`): модель получает данные в теге
   `<product_data>` и строгие правила: использовать только входные данные.
   Ответ в формате JSON по образцу.
4. **Автоматическая проверка** (`validation.py`): длина заголовка и описания,
   число запросов, числа в тексте должны быть и во входных данных, слова
   запросов должны встречаться во входных данных, запрещены «украшения»
   вроде «надёжный» и «качественный». При замечаниях модель переделывает
   текст (до 3 попыток), а оставшиеся замечания попадают в «Требует внимания».
5. **Сборка карточки** (`generator.py`, `render.py`): список характеристик
   и список недостающих данных формирует код, а не модель.

## Ограничения

- Сервис протестирован на локальной модели `qwen2.5:7b`. Модели такого размера
  иногда пишут слипшиеся слова, неточно формулируют смысл и обходят запреты.
  Проверка ловит числа и часть «украшений», но не любую выдумку: например,
  неверное свойство без числа в тексте код не распознаёт. **Текст перед
  публикацией должен прочитать человек.**
- Объём SEO-описания зависит от количества входных данных. На скудных данных
  описание получается короче 800 символов, и сервис честно об этом предупреждает,
  а не растягивает текст выдумками.
- Список недостающих данных строится по фиксированным правилам (производитель,
  характеристики, описание), а не по смыслу товара.
- Нет веб-интерфейса, автотестов и учёта разных типов приборов.

## Возможные улучшения

- Более сильная модель (облачный API): лучше русский текст и точнее выполнение правил.
- Проверка покрытия: все характеристики и факты из описания должны быть в тексте.
- Семантическая проверка утверждений (вторым вызовом модели: «есть ли опора
  на входные данные»).
- Шаблоны недостающих данных по типу прибора (манометр, термометр и т.д.).
- Простая веб-форма и пакетная загрузка из таблицы.
- Автотесты на `validation.py` и `loader.py`.

## Структура проекта

```
main.py              CLI
check_setup.py       проверка настройки
cardgen/
  config.py          настройки из .env
  models.py          модели данных (вход, ответ модели, карточка)
  loader.py          чтение и валидация входного JSON
  validation.py      пробелы во входе, проверка ответа модели
  prompts.py         системный промпт
  llm.py             вызов модели, обработка ошибок API
  generator.py       цикл генерации и сборка карточки
  render.py          вывод в Markdown
examples/            входные данные и примеры результатов
```
